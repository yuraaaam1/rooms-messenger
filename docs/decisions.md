# Согласованные архитектурные решения

## ADR-001. Раздельные криптографические ключи пользователя

**Дата:** 2026-10-07  
**Статус:** согласовано

### Решение

Каждый пользователь использует две независимые пары ключей P-256:

- ECDH — для получения общего секрета и вывода AES-ключа;
- ECDSA — для цифровых подписей входа, сообщений и управляющих запросов.

### Причина

Ключи разделяются по назначению: обмен секретом и цифровые подписи.
Один объект `CryptoKey` имеет конкретный алгоритм и разрешённые операции.
Повторный импорт подходящего EC-ключевого материала с другим назначением
технически возможен, поэтому две независимые пары — согласованное
архитектурное решение, а не единственный технически возможный вариант.

### Последствия

На сервере для участника будет храниться набор из двух публичных JWK-ключей.
Закрытые ключи останутся только на устройстве пользователя.

## ADR-002. Стиль серверной архитектуры

**Дата:** 2026-10-07  
**Статус:** согласовано

### Решение

Использовать выборочно подход из pet-проекта:

- ручная dependency injection;
- разделение transport, service и repository;
- интерфейсы на границе service и repository;
- DTO для HTTP-запросов;
- feature-first структура по мере роста приложения.

### Ограничения

Не используются PostgreSQL, Redis, Docker как обязательная зависимость,
API versioning и другие компоненты, не требуемые ТЗ.

## Конвенции клиентского кода

- По предпочтению пользователя собственные переменные, параметры, функции
  и поля объектов именуются в camelCase; для шифротекста используется cipherText.
- Константы сохраняют принятую запись UPPER_SNAKE_CASE.
- Имена полей Web Crypto/JWK и утверждённых внешних форматов не переименовываются
  ради стиля, например namedCurve, crv и key_ops.
- Использование cipherText вместо ciphertext в собственном внутреннем объекте
  не изменяет криптографический алгоритм или требования ТЗ.

## Журнал реализации

### 2026-10-08. Проверка JSON-запросов создания комнаты

Внесены исправления по согласованным замечаниям ревью:

- Content-Type сравнивается точно, параметры вроде charset допускаются.
- Размер тела ограничен настройкой max_json_request_size_bytes: сейчас 64 КиБ.

- JSON-объект отличается от массива; пустой объект проходит к проверке полей.
- Пользователь подтвердил ожидаемые ответы HTTP 415 и 400 после исправления.

Лимит относится к текущему JSON-обработчику, а не к будущей передаче файлов.
Формат метаданных комнаты и криптографические требования не изменены.

### 2026-10-10. Надёжная запись метаданных новой комнаты

- JSON сериализуется до создания директории комнаты.
- created_at сохраняется строкой DATE_ATOM, как в исходном формате meta.json.
- Директория создаётся через mkdir; существующий ID не перезаписывается.
- JSON сначала записывается в .meta.json.tmp в директории новой комнаты.
- Проверяется точное число записанных байтов, затем rename публикует meta.json.
- При обрабатываемой ошибке удаляются временный файл и пустая директория,
  созданные этой операцией; неудачная уборка записывается в лог.
- Ошибка сериализации преобразуется в RuntimeException с сохранением причины.

Текущий код проверен в отдельном хранилище в /tmp: обычное сохранение,
строковый created_at, повторный ID, невалидный UTF-8, смоделированные ошибки
записи/частичная запись и отказ rename, восемь параллельных операций одного ID.
Пользователь подтвердил HTTP 201; исправление форматирования даты проверено
в исходнике и отдельном тесте репозитория.

Это атомарная публикация одного файла на локальной файловой системе Linux,
не транзакция нескольких файлов и не гарантия уборки при аварийном завершении
процесса или сохранности при сбое питания. В будущем чтение должно отличать
готовые метаданные от ещё не опубликованной комнаты.
API и требования ТЗ не меняются.

### 2026-10-10. Генерация ключей пользователя

Добавлен public/assets/js/crypto/keys.js:

- generateUserKeys создаёт независимые пары ECDH P-256 и ECDSA P-256.
- Закрытый ECDH-ключ разрешает deriveBits, закрытый ECDSA-ключ — sign;

- extractable: true позволяет впоследствии экспортировать закрытые ключи
  для шифрования перед локальным сохранением.

Текущий исходник отдельно проверен средствами Node.js Web Crypto: алгоритмы,
кривые и разрешённые операции, отсутствие закрытого параметра d в публичных

секрета ECDH у двух сторон. Сквозная интеграция в интерфейс ещё не выполнена.
Пользователь также подтвердил три успешные проверки в браузере: ECDH P-256,
ECDSA P-256 и отсутствие d в обоих публичных JWK. Ошибки scdsa/srv находились
в консольной проверке; исправления keys.js для их устранения не требовались.

«Ключевой контейнер» — рабочее название данных для зашифрованного хранения
закрытых ключей, не новая функция или изменение требований ТЗ. В разделе 5.2
ТЗ заданы PBKDF2-SHA-256, соль 32 байта, 200 000 итераций и AES-256-GCM;
конкретная JSON-схема контейнера пока не зафиксирована.
На этом шаге закрытые ключи ещё не сохраняются в localStorage.

### 2026-10-10. Получение ключа защиты контейнера из личного пароля

Добавлен public/assets/js/crypto/password.js:

и запрет экспорта. В исходнике исправлены AES_GCM на AES-GCM и строковая

Текущий исходник отдельно проверен средствами Node.js Web Crypto:
результат согласуется с независимым node:crypto pbkdf2Sync; повторный вывод
даёт ключ, которым расшифровываются тестовые данные. Проверены отклонение
экспорта, пустого пароля и соли неправильной длины. При проверке с предлагаемым
AES-GCM помощником неверный пароль и изменённая соль приводили к отказу
расшифровки. Сам AES-GCM помощник пока только предложен, в проект не внесён.

Это ключ локальной защиты закрытых ключей, не результат ECDH и не ключ
переписки. Цепочка ECDH -> HKDF -> попарный AES остаётся отдельным этапом.
Контейнер, его сохранение и разблокировка пока не реализованы.
Требования ТЗ не изменены.

### 2026-10-10. Шифрование байтов AES-GCM

Добавлен public/assets/js/crypto/aes.js с encryptBytes и decryptBytes:

- Функции принимают готовый AES CryptoKey и данные в Uint8Array.
- Для каждого шифрования генерируется новый случайный IV длиной 12 байт.
- Используется метка аутентификации 128 бит, включённая Web Crypto в результат.
- encryptBytes возвращает объект с полями iv и cipherText, оба Uint8Array.
- Проверяются типы данных, длина IV и минимальная длина шифротекста с меткой.
- Ошибки проверки метки при расшифровке не подавляются.

Пользователь подтвердил в браузере три проверки: IV длиной 12 байт,
восстановление текста и отклонение изменённого шифротекста. В консольном
тесте исправлены пропущенный await и опечатка в имени decryptBytes;
проверка адаптирована к фактическому полю cipherText.

Текущий исходник отдельно проверен средствами Node.js Web Crypto:
пустые и бинарные данные, восстановление UTF-8 текста, длина результата
с 16-байтовой меткой, неверный ключ, изменение шифротекста, IV и метки,
некорректные аргументы. Приложение пока не шифрует и не сохраняет закрытые
ключи: помощник encryptPrivateKeys только предложен на следующем микро-шаге.
Никакие тестовые данные не сохранялись в localStorage или хранилище проекта.
Требования ТЗ не изменены.

Актуальная функция шифрования отдельно проверена средствами Node.js Web Crypto

подписать сообщение с проверкой исходным публичным ключом и получить общий

Это зашифрованный блок закрытых ключей, не законченная локальная идентичность:
соль, версия локальной записи, публичные ключи, сохранение, проверка соответствия

Сохранение/чтение localStorage, проверка версии и структуры всей записи,

### 2026-10-11. Сборка локальной записи идентичности

В public/assets/js/identity.js добавлена createIdentityRecord:

- Проверяет строковый непустой никнейм и удаляет его краевые пробелы.
- Создаёт соль и получает masterKey из личного пароля через текущий PBKDF2-помощник.
- Генерирует независимые ECDH/ECDSA пары, экспортирует публичные JWK и шифрует закрытые.
- Возвращает JSON-сериализуемую запись версии 1: version, nickname, publicKeys,

- Не возвращает пароль, masterKey или открытые закрытые JWK; не обращается
  к localStorage, серверу и DOM. Каждый вызов создаёт новую идентичность.

Пользователь подтвердил браузерную проверку записи. Текущий исходник отдельно
проверен средствами Node.js Web Crypto: JSON round-trip, нормализация никнейма,
восстановление закрытых ключей и проверка подписи сохранённым публичным ключом.

Следующим микро-шагом предложен validateIdentityRecord: синхронная проверка
версии, объектов, никнейма, структуры публичных JWK без d, стандартного Base64
и длин соли/IV/шифротекста. Валидатор возвращает исходный объект без изменения;
он не очищает произвольные дополнительные поля и не является проверкой пароля,
криптографической корректности координат JWK или соответствия ключевых пар.
Импорт публичных ключей и проверка соответствия остаются отдельными шагами.

Предлагаемый валидатор независимо проверен: корректная запись принимается без
изменений, отклонены 32 случая неверной структуры. Изменение байта шифротекста
при сохранении формата проходит структурную проверку, но отклоняется AES-GCM;
неверный пароль также отклоняется при расшифровке. Валидатор пока не внесён
пользователем и выполненным не отмечен. Сохранение/чтение, защита от перезаписи
и полная разблокировка ещё не реализованы. Тесты не сохраняли данные в localStorage.

По просьбе пользователя дальнейшие объяснения включают роль каждого модуля,
входные/выходные данные, цепочку вызовов и ограничения каждого шага.
Требования ТЗ не меняются.

QuotaExceededError/SecurityError. Реальный localStorage в тестах не использовался.

после перезагрузки остаются в плане. Требования ТЗ не меняются.

### 2026-10-18. Предложен обработчик создания профиля

Следующий микро-шаг расширяет только identityUI.js; main.js и HTML остаются

третий необязательный аргумент locks позволяет подставить LockManager в тесте.

Порядок сценария:

1. Синхронно вызвать preventDefault, проверить повторную отправку/состояние формы.
2. Выполнить HTML-валидацию, проверить никнейм после trim и совпадение паролей.

4. Проверить её через unlockIdentity и получить рабочие CryptoKey без экспорта.
5. Дождаться saveIdentityRecord под существующей именованной Web Locks-блокировкой.
6. Только после успеха присвоить подготовленный объект activeIdentity и показать
   готовность. JSON-запись сохраняется, рабочий объект ключей остаётся в памяти.

activeIdentity и creationInProgress — локальные переменные инициализации,
удерживаемые зарегистрированным обработчиком-замыканием. Защита от повторного
