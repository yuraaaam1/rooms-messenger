## 1. Самое важное: где остановились

Разрабатываем браузерный зашифрованный мессенджер. Серверная основа создания комнаты и клиентская криптография профиля уже реализованы. Сейчас подключаем криптографические функции к обычным HTML-формам.

**Последний выданный шаг — обработчик создания профиля в `public/assets/js/identityUI.js`. При подготовке этой сводки файл прочитан: пользователь уже внёс обработчик. Однако результата его проверки в браузере пользователь ещё не присылал.**

Не выдавать этот обработчик заново как отсутствующий. Не считать весь сценарий создания через UI проверенным. Первый шаг нового чата — сверить файл и проверить создание профиля, затем состояние после перезагрузки. После успешной проверки подключить обработчик входа/разблокировки существующего профиля.

Последний подтверждённый скриншотом результат до добавления обработчика: сервер доступен, приложение определяет отсутствие сохранённой записи и показывает форму создания. Изначально поля были отключены. Новый обработчик должен включать их при отсутствии записи и наличии Web Locks.

## 4. Утверждённая основа архитектуры

- Backend: PHP, JSON-файлы, без обязательной внешней СУБД.
- Frontend: обычные HTML и JavaScript ES modules, Web Crypto API, без обязательного сборщика.
- Получение сообщений: HTTP polling, не WebSocket.
- Сервер не должен получать личный пароль и закрытые ключи пользователя; будущие сообщения хранятся зашифрованными.
- `localStorage` используется для локального ключевого контейнера и будущей истории согласно ТЗ. IndexedDB без разрешения не подменять.
- Пароль комнаты и личный пароль — разные сущности. SHA-256-хеш пароля комнаты предусмотрен текущим ТЗ; не заменять протокол на PAKE или другой механизм молча.
- Клиентская криптография работает в secure context: для разработки использовался `http://127.0.0.1:8080`, для выпуска нужен HTTPS.
- Ручная dependency injection и разделение HTTP / application service / repository / domain.
- Не добавлять обязательные PostgreSQL, Redis, Docker, framework, API versioning или сборщик без необходимости и согласования.

Согласованные решения:

- **ADR-001, 07.10.2026:** две независимые пары P-256: ECDH для общего секрета, ECDSA для подписей. Это согласованное архитектурное решение, а не утверждение, что повторный импорт EC-материала с другим назначением технически невозможен.
- **ADR-002, 07.10.2026:** полезные идеи gotodoapp — ручная DI, transport/service/repository, интерфейс репозитория, DTO и группировка по фичам по мере необходимости. DTO и feature-first не следует считать уже повсеместно реализованными.

## 7. Что реализовано на PHP

### HTTP

- `GET /api/health` → JSON с `status`, `app`, `time`.
- `POST /api/room/create` → создание только метаданных комнаты.
- Создание ожидает JSON:

```json
{
  "name": "Тестовая комната",
  "password_hash": "<64 hex-символа SHA-256>"
}
```

- Ответ создания — `201` с `id`, `name`, `created_at`, без возврата хеша пароля.
- Для создания проверяется POST, иначе `405` с `Allow: POST`.
- Проверяется Content-Type `application/json`, допускается параметр charset; неподходящий тип → `415`.
- Лимит JSON-тела — 64 KiB, читается лимит + 1; превышение → `413`.
- Неверный JSON и JSON не-объект, включая массив, → `400`. Декодирование сначала в объект, затем `get_object_vars` позволяет не путать `{}` и `[]`.
- `JsonResponse::send()` устанавливает JSON UTF-8 и `X-Content-Type-Options: nosniff`, кодирует с исключениями, завершает выполнение.

### Модель и хранение

- `Room`: readonly id, name, passwordHash, DateTimeImmutable createdAt.
- ID — 32 lowercase hex-символа из `random_bytes(16)`; хеш — 64 lowercase hex; имя непустое.
- `RoomService` зависит от интерфейса `RoomRepository`, не от конкретного JSON-репозитория.
- Интерфейс пока содержит только `saveNew(Room $room): void`.
- `JsonRoomRepository` сохраняет `data/rooms/<id>/meta.json`.
- Дата сериализуется строкой DATE_ATOM, не объектом DateTime.
- JSON формируется до создания каталога.
- Новый каталог создаётся с 0700; существующий ID не перезаписывается.
- Сначала записывается `.meta.json.tmp`, проверяется число байтов, затем `rename` публикует `meta.json`.
- При ошибке предусмотрена уборка временного файла/незавершённого каталога.
- Проверены ошибки записи, повторный ID и параллельные попытки; см. журнал.

**Границы:** это ещё не полноценное создание комнаты с администратором и участниками. `admin.json`, `participants.json`, `blocked.json` не реализованы. Атомарность текущего `meta.json` не означает транзакцию нескольких файлов или доказанную устойчивость к сбою питания.

**Открытый пункт до следующих интеграций API:** единая обработка неожиданных серверных исключений с JSON-ответом. Не считать её уже реализованной только потому, что отдельные ошибки ловит RoomController.

## 8. Криптографические цепочки: не путать

Уже реализовано:

```text
Личный пароль → PBKDF2-SHA-256 → AES-256-GCM → защита контейнера закрытых ключей
```

Ещё предстоит реализовать для сообщений:

```text
Закрытый ECDH + публичный ECDH собеседника → общий секрет → HKDF-SHA-256 → AES-ключ
```

Сейчас нет HKDF для переписки и нет шифрования/доставки сообщений. Наличие ECDH в проверке согласованности ключей не означает готовую переписку.

Параметры реализованной защиты контейнера:

- PBKDF2, SHA-256, 200 000 итераций.
- Случайная соль 32 байта.
- AES-GCM, ключ 256 бит, случайный IV 12 байт, tag 128 бит.
- Ключ защиты контейнера: `extractable: false`, usages encrypt/decrypt.
- Исходные пары ECDH/ECDSA генерируются с возможностью экспорта закрытой части для упаковки в контейнер.
- При разблокировке закрытые ключи импортируются с `extractable: false`: ECDH usages deriveBits, ECDSA usages sign.
- Публичный ECDH используется с пустыми usages, публичный ECDSA — verify.

`deriveBits` у ECDH выбран для будущего вывода через HKDF, а не прямого превращения общего секрета в ключ AES.

### Именование и кодировки

- Собственные поля/функции — camelCase. Для шифротекста пользователь предпочитает **`cipherText`**, не `ciphertext`.
- Имена Web Crypto/JWK не переименовывать: `namedCurve`, `crv`, `key_ops` и т. п.
- PHP HTTP-контракт и файловые метаданные уже используют `password_hash`, `created_at`; не переименовывать внешние форматы ради стиля.
- Соль/IV/шифротекст локальной записи — обычный канонический Base64 с padding.
- Координаты JWK — Base64URL, их обрабатывает Web Crypto. Отдельный Base64URL helper остаётся в TODO; нельзя декодировать JWK-координаты обычным Base64 helper без учёта формата.
- Формат будущего сообщения по текущему плану ТЗ — `ivBase64:ciphertextBase64`. Он ещё не реализован и не равен внутреннему объекту `{iv, cipherText}`.

## 9. Контракты клиентских модулей

### `encoding.js`

`textToBytes`, `bytesToText`, `bytesToBase64`, `base64ToBytes`.

UTF-8 decoder с fatal-проверкой; Base64 decoder проверяет каноничность повторным кодированием. `bytesToBase64` принимает ArrayBuffer view и учитывает byteOffset/byteLength. Проверены русский текст и бинарные значения; `[0, 1, 127, 128, 255]` кодируется как `AAF/gP8=`.

### `keys.js`

- `generateUserKeys()` → `{ecdh: CryptoKeyPair, ecdsa: CryptoKeyPair}`.
- `exportPublicKeys(keys)` → `{ecdh: publicJwk, ecdsa: publicJwk}`.
- `importPublicKeys(publicKeys)` → `{ecdh: publicCryptoKey, ecdsa: publicCryptoKey}`.
- Публичные JWK с полем `d` отклоняются; ожидается P-256.

Не путать возвращаемые пары с плоским набором импортированных CryptoKey.

### `password.js`

- `createPasswordSalt()` → Uint8Array 32 байта.
- `derivePasswordKey(password, salt)` → Promise<CryptoKey AES-GCM>.
- **Вызов требует await.** В прошлых проверках забытый await приводил к передаче Promise вместо CryptoKey.

### `aes.js`

- `encryptBytes(key, plainBytes)` → Promise<{iv: Uint8Array, cipherText: Uint8Array}>.
- `decryptBytes(key, iv, cipherText)` → Promise<Uint8Array>.
- Неверный пароль/изменённый шифротекст не принимаются как успешная расшифровка.

### `keyContainer.js`

- `encryptPrivateKeys(keys, masterKey)` экспортирует две закрытые JWK, упаковывает JSON, шифрует и возвращает Base64 `{iv, cipherText}`.
- `decryptPrivateKeys(encrypted, masterKey, expectedPublicKeys)` расшифровывает, проверяет закрытые JWK и **до импорта** сверяет их `kty/crv/x/y` с внешними публичными JWK.
- Третий аргумент обязателен. Возвращается плоский набор `{ecdh: privateCryptoKey, ecdsa: privateCryptoKey}`.
- Внутренний синхронный помощник называется `assertPublicJwkMatches`; он не равен асинхронной функциональной проверке из keyChecks.

### `keyChecks.js`

`assertKeyPairsConsistent(privateKeys, publicKeys)`:

- ECDSA: случайный challenge → подпись → проверка.
- ECDH: временная пара, два способа получения секрета, сравнение байтов; временные массивы секретов очищаются в finally.

Важный уже разобранный нюанс: ECDH по x-координате секрета сам по себе не различает публичные точки Q и −Q. Поэтому функциональная проверка **дополнена точным сравнением публичных координат с JWK внутри контейнера**. Не убирать эту привязку как «дублирование».

### `identity.js`

- `createIdentityRecord(nickname, password)` → новая локальная запись. Не сохраняет её и не обращается к DOM/серверу. Каждый вызов генерирует новую идентичность.
- `validateIdentityRecord(record)` → проверяет объект, version=1, непустой никнейм, форму публичных JWK без d, канонический Base64 и длины соли/IV/шифротекста. Возвращает тот же объект. Это структурная проверка, не разблокировка.
- `restoreIdentityPrivateKeys(record, password)` → закрытые CryptoKey; использует сохранённую соль, PBKDF2 и decryptPrivateKeys с expectedPublicKeys.
- `unlockIdentity(record, password)` → делает structuredClone записи, восстанавливает закрытые ключи, импортирует публичные, проверяет пары, возвращает рабочий объект.

Формат сохранённой записи:

```javascript
{
    version: 1,
    nickname: 'Имя',
    publicKeys: {
        ecdh: { kty: 'EC', crv: 'P-256', x: '...', y: '...' },
        ecdsa: { kty: 'EC', crv: 'P-256', x: '...', y: '...' },
    },
    keyContainer: {
        salt: 'обычный Base64',
        iv: 'обычный Base64',
        cipherText: 'обычный Base64',
    },
}
```

Рабочий результат unlockIdentity:

```javascript
{
    nickname: 'Имя',
    privateKeys: { ecdh: CryptoKey, ecdsa: CryptoKey },
    publicKeys: { ecdh: CryptoKey, ecdsa: CryptoKey },
}
```

Рабочий объект не сериализовать и не сохранять вместо записи. В нём нет личного пароля, masterKey или контейнера. Формат локального record пока не является утверждённым форматом серверного участника.

### `storage/identityStorage.js`

```javascript
IDENTITY_STORAGE_KEY = 'messenger.identity';
IDENTITY_WRITE_LOCK = 'messenger.identity.write';

loadIdentityRecord(storage = globalThis.localStorage);

saveIdentityRecord(
    record,
    storage = globalThis.localStorage,
    locks = globalThis.navigator?.locks,
);
```

- Чтение синхронное. `null` возвращается только при отсутствии значения.
- Повреждённый JSON, неизвестная версия и отказ доступа — исключения. Данные не удаляются, пустой профиль автоматически не создаётся.
- Сохранение асинхронное; **все вызовы должны await его результат**.
- До ожидания создаётся и валидируется глубокий снимок.
- Под одной exclusive Web Lock выполняются проверка отсутствия любого значения и запись.
- Любое существующее значение, включая пустую/повреждённую строку, запрещает перезапись.
- Сохраняется только явная проекция полей; публичные JWK копируются как kty/crv/x/y, лишние поля исключаются.
- Внутренняя `writeIdentityRecord` не экспортируется.
- При отсутствии Web Locks — отказ, без небезопасного fallback.
- Это кооперативная блокировка писателей приложения, не защита от XSS, прямого setItem или старой вкладки с другим кодом.

## 10. Текущий UI и последний внесённый код

`main.js` проверяет secure context и Web Crypto, один раз вызывает `initializeIdentityUI()`, затем выполняет GET /api/health. Выбор локального экрана не зависит от успешности health-запроса. Инициализация UI сейчас синхронная; main не получает из неё контроллер или объект ключей.

HTML содержит:

- `identity-create-form` внутри `identity-create-section`.
- Никнейм `identity-create-nickname`.
- Пароли `identity-create-password` и `identity-create-password-confirmation`.
- `identity-create-fields` — fieldset, изначально disabled в HTML.
- `identity-unlock-form`, `identity-unlock-password`, `identity-unlock-fields` внутри скрытого `identity-unlock-section`.
- `identity-stored-nickname` для найденной записи.
- Скрытый `identity-ready-section`, никнейм `identity-nickname`.
- `identity-feedback` для сообщений, `app-status` для состояния клиента/сервера.

Две формы не вложены одна в другую, есть labels, required, autocomplete. Вывод пользовательских значений через textContent, не innerHTML.

### Что теперь есть в `identityUI.js`

Сигнатура:

```javascript
initializeIdentityUI(
    root = globalThis.document,
    storage,
    locks = globalThis.navigator?.locks,
);
```

Необязательные зависимости предназначены для подставных тестов. Значение localStorage по умолчанию подставляется внутри loadIdentityRecord, вызванной под try, чтобы поймать в том числе ошибку getter localStorage.

Внутри инициализации находятся `activeIdentity = null`, `creationInProgress = false` и вложенный `handleCreateSubmit`. Обработчик-замыкание удерживает эти переменные после завершения инициализации. **Экспортированного getActiveIdentity или globalThis.activeIdentity сейчас нет.**

Порядок создания:

1. Установить submit-обработчик до включения fieldset.
2. При отсутствии записи и наличии Web Locks включить только форму создания. Форма входа пока отключена.
3. В начале submit синхронно вызвать preventDefault.
4. Отклонить повторный запуск, скрытую/отключённую форму, уже активный профиль.
5. Выполнить reportValidity, trim никнейма, проверку на пробельное имя и совпадение паролей. Пароль не trim.
6. При несовпадении очистить подтверждение и оставить возможность исправить ввод.
7. Поставить busy-флаг и отключить поля.
8. Выполнить существующую криптографическую цепочку:

```javascript
const record = await createIdentityRecord(normalizedNickname, password);
preparedIdentity = await unlockIdentity(record, password);
await saveIdentityRecord(record, storage, locks);
```

9. В finally очистить переменную пароля и оба поля, снять busy-флаг. Это не обещание гарантированного стирания всех копий строки из памяти JS.
10. Только после успешного save присвоить `activeIdentity = preparedIdentity`, сбросить форму и показать готовность.

Если подготовка или сохранение бросает ошибку, catch показывает сообщение и делает return. После finally код активации не выполняется. Поля временно остаются отключёнными; предлагается перезагрузка и повторное чтение, поскольку конкурентная вкладка могла сохранить другой профиль. Никаких удалений/перезаписей для восстановления UI нет.

Подготовка через unlockIdentity намеренна: проверяем весь путь восстановления и получаем неэкспортируемые рабочие закрытые ключи, а не используем исходные экспортируемые пары из генератора.

«Профиль готов» пока означает готовность ключей в памяти, не работающие комнаты, переписку или серверную аутентификацию.

### Первые действия нового чата

1. Сверить текущий identityUI.js с описанием; не заменять файл вслепую.
2. Запустить приложение на ноутбуке и проверить браузерную консоль при проблемах.
3. При отсутствии записи форма создания должна включиться.
4. Проверить разные пароли: понятная ошибка, профиль не создан.
5. Создать учебный профиль с одинаковыми паролями, которые пользователь запомнит. Пароль в чат не присылать.
6. Убедиться в появлении готовности с никнеймом.
7. Перезагрузить страницу на том же origin: должен появиться найденный профиль и отключённая форма входа. Это ожидаемо до следующего шага.
8. Если профиль уже есть, не удалять его ради теста. Можно использовать отдельный тестовый профиль браузера; сначала учитывать различие окружений ПК/ноутбука.
9. После подтверждения обновить TODO/журнал и подключить `handleUnlockSubmit` отдельным понятным шагом.

### Требования к следующему обработчику входа

- Установить submit с preventDefault до включения полей.
- Повторно прочитать существующую запись, а не молча использовать устаревшую копию.
- Вызвать `await unlockIdentity(record, password)`.
- Не активировать профиль при ошибке/неверном пароле; дать понятное сообщение и возможность повторного ввода.
- Не удалять запись при ошибке, не сохранять новую поверх неё.
- После успеха установить рабочую идентичность в памяти и показать готовность.
- Очистить поля пароля; пользовательские значения выводить через textContent.
- Разблокировка не требует повторного сохранения record и не должна зависеть от возможности захватить write-lock.
- Проверить неверный пароль, правильный пароль и перезагрузку; затем проверить конфликт создания из двух вкладок на уровне UI.

## 11. Что уже проверено и какие есть границы

Пользователь ранее подтвердил в браузере:

- UTF-8/Base64, генерацию двух пар, экспорт публичных JWK без d.
- PBKDF2 и AES-GCM, восстановление текста, отказ при повреждении шифротекста.
- Шифрование/расшифровку закрытых ключей и запрет экспорта после восстановления.
- Структуру локальной записи и отказ для некорректных полей/длин/версии.
- Чтение/сохранение на подставном Storage без перезаписи и без удаления повреждённых данных.
- Восстановление ключей по паролю, импорт публичных JWK, согласованность пар.
- Отклонение подмены публичных ключей/изменённых координат при привязке к контейнеру.
- Единую unlockIdentity.
- Реальные сохранение в localStorage → перезагрузку → чтение → разблокировку; контрольная сумма сохранённой строки до и после совпала.
- Очередь настоящего Web Locks в одной вкладке с подставным Storage.
- Две вкладки одного origin: A держит именованную блокировку, B ожидает без чтений/записей подставного Storage; после освобождения одна запись и успешное восстановление. clientId разные, настоящий localStorage не изменён.
- Выбор начального экрана без записи и работу health после исправления импорта .js.

Ассистент также выполнял независимые проверки с Node.js Web Crypto, подставными DOM/Storage/LockManager; для PHP — в отдельных временных хранилищах. Эти проверки не оформлены как готовый постоянный набор тестов в репозитории и не заменяют нативный браузерный UI-тест.

Для последнего предложенного обработчика создания отдельно проверялись: несовпадение паролей/пробельный никнейм, busy-поведение, отсутствие готовности до окончания save, запрет повторного submit, очистка паролей, ошибки квоты/доступа/отсутствие Web Locks, конкурентные формы с одним победителем, отсутствие перезаписи появившейся повреждённой записи. **Это были проверки предложенного кода. При создании сводки фактический файл осмотрен, но новый браузерный результат пользователя ещё отсутствует.**

### Уже разобранное сообщение Firefox: не начинать расследование заново без новых фактов

В Firefox 157 на Ubuntu тесты намеренно бросающих исключения Web Locks callback показывали красное `Uncaught (in promise)` даже при rejected-результатах в Promise.allSettled. Синхронный и async callback давали одинаковое наблюдение.

Отдельный диагностический тест подтвердил обработанный возвращённый Promise и пустой массив событий error/unhandledrejection за секунду наблюдения при наличии красной строки. Это зафиксировано как ограниченное наблюдение окружения, **не доказанный конкретный баг браузера и не доказательство отсутствия любых ошибок**.

Не менять callback на async и не подавлять глобальные ошибки ради этой строки. Другие неожиданные ошибки всё равно исследовать по фактам.

## 13. Что ещё предстоит после профиля

Ближайшая последовательность, без переписывания готовых модулей:

1. Подтвердить создание профиля через UI и подключить вход после перезагрузки.
2. Закрыть единый JSON-ответ при неожиданных серверных ошибках до следующих API-интеграций.
3. Сверить с ТЗ и согласованным разделением ключей серверный формат участника и публичного набора. Пока не считать локальный JSON готовым HTTP-контрактом.
4. Расширить создание комнаты: хеш пароля, ключи создателя, права администратора, согласованная запись нескольких файлов.
5. Проверить совместимость формата ECDSA-подписей JavaScript и PHP.
6. Внедрить вход по паролю комнаты с подписью timestamp, проверкой срока и блокировок согласно ТЗ. Точный протокол не придумывать вместо согласованного.
7. ECDH → HKDF → AES для сообщений; согласовать одинаковые salt/info и подписываемые байты.
8. Подпись и шифрование текста, серверный send, хранение ciphertext, poll, расшифровка и проверка подписи до отображения.
9. Принять прототип на двух независимых профилях, включая ошибки, перезагрузку и демонстрацию руководителю.

Полная версия затем включает групповые ключи и их обновление, управление комнатой/паролем/блокировками/удалением, фрагментированную передачу файлов, локальную историю, экспорт/импорт backup, HTTPS, надёжность и документацию. Детальные микро-шаги — в TODO.md; это не уже реализованные функции.

Не добавлять «для полноты» серверные аккаунты, JWT, WebSocket, новую СУБД, PAKE или другой способ хранения без запроса/согласования.

### Открытые вопросы ТЗ, не разрешённые самовольно

- Polling: расхождение 1 секунда и рекомендации 10–120 секунд.
- Поиск/доступ при одинаковом пароле разных комнат.
- Идентификация пользователя после введения двух публичных ключей.
- Защита от повторного запроса внутри допустимого окна timestamp.
- Порядок/курсор сообщений при одинаковых timestamp.
- Групповая комната при отсутствии создателя в сети.
- Совместимость потокового скачивания с целевыми браузерами.
- Потоковый SHA-256 и конфиденциальность файловых метаданных.

Эти вопросы не являются разрешением менять ТЗ и не должны останавливать независимую работу над профилем.
